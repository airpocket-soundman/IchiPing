Solist-AI 移植 — 技術的課題まとめ（v2 実証スコープ）

v1（FRDM-MCXN947 + 自由 1D-CNN）を v2（ROHM ML63Q2557 + Solist-AI ELM/マハラノビス）に持っていくとき、実装上どこで詰まるかを集約したページ。 spec.html §10 / §11 / §12-Phase2 で確定済みのアーキ方針を起点に、ハード・信号処理・推論・ツール・検証の 5 軸でリスクと確認事項を列挙する。
Cortex-M0+ 48 MHz / FPU 無 16 KB RAM 目標 14 クラス × D=30 次元 ELM ×4 + マハラノビス

1. このページのスコープ

spec.html §11 にあるとおり、v1→v2 は機能拡張ではなく同じ問題（同じ実験模型・同じデータセット・同じ推論ターゲット）を 2 つの NN プラットフォームで並列に解く形。本ページは v2 側の 移植実装に絞り、設計判断のうち 確定・仮定・未確認 を区別して列挙する。

  • 確定: spec.html §10/§11/§12 に明記されたアーキ方針（ELM ×4、マハラノビス、AxlCORE-ODL、目標 17 KB、目標 1 ms 推論）
  • 仮定: 一般的な Cortex-M0+ MCU の性質からの推定（FPU 無、固定小数前提、CMSIS 流儀の API 等）
  • 未確認: ROHM 開発キット入手後に必ず確認すべき仕様事項（I/F 種別、SDK 詳細、自己書込み API 等）

実家屋デプロイは 本プロジェクトのスコープ外（spec.html §11 末尾）。実験模型上での動作実証だけを評価対象とする。

2. v1 → v2 スタック差分（俯瞰）

3. 信号処理パイプライン

v1 では NPU が生 raw 信号を直接食えるため、特徴抽出を簡略化できた。v2 では NN 入力が手前で D=30 の物理特徴量に圧縮されている（spec.html §10 入力欄）ので、特徴抽出パイプラインを M0+ 上で実時間で回すのがキーになる。

3.1 chirp 生成

  • 200 Hz → 8 kHz 線形チャープ × 2 秒（16 kHz サンプリング = 32k サンプル）
  • v1: render_chirp() が sinf() で実時間生成（FPU 有なので軽い）
  • v2: FPU 無で sinf() は重い → 事前生成した int16 チャープテーブル（32 KB）を Flash に焼くのが現実的。再生回数が高々数回/秒なら RAM コピー不要、Flash 直アクセスで足りる
  • fade-in/out（v1 で 5 ms）も事前にテーブル化

3.2 マイク取得

  • v1: I²S 32-bit ステレオ→ MonoRight 抽出 + float 化（INMP441 / MSM261S4030H0）
  • v2 で I²S が無く PDM のみなら、decimation FIR を CPU で実装する必要あり
    • 3.072 MHz PDM → 16 kHz PCM = decimation by 192 倍。多段（CIC + half-band）で M0+ 実時間が成立するか要検証
    • CMSIS-DSP arm_fir_decimate 相当が ROHM SDK にあれば流用、無ければ自前実装
  • I²S/PDM どちらも無ければ 外付け codec（I²C 制御 + I²S 出力）または別マイクの選定が必須 → BOM 影響大

3.3 特徴抽出（30 次元への圧縮）

spec.html §10 で RT60 × 8 帯 + DRR × 3 + モードピーク × 6 + 振幅 × 6 + ノイズ床 × 3 = 26〜30 次元、と確定。M0+ 実装でのボトルネック候補:

特徴量必要処理想定コスト / リスク
RT60 × 8 帯8 帯域フィルタバンク（IIR バタワース等）→ エネルギー減衰の対数線形回帰32k サンプル × 8 帯 のリングバッファ保持は RAM 16 KB に乗らない → 帯域ごとに逐次計算 + ダウンサンプリング前提
DRR × 3直接音 / 残響成分のエネルギー比、3 帯onset 検出が要、ピーク+50 ms 窓と +50〜500 ms 窓のパワー比
モードピーク × 6低域 (~500 Hz) FFT のピーク周波数と QFFT 512 or 1024 を 固定小数で M0+ @ 48 MHz が間に合うか要計測。CMSIS-DSP arm_rfft_fast_q15 相当が無ければ自前
振幅 × 66 帯のピーク振幅RT60 のフィルタバンク出力を流用可
ノイズ床 × 3chirp 開始前 100 ms × 3 帯のパワー軽い。要するに pre-chirp 区間の RMS

順番が大事: chirp 開始前 100 ms（ノイズ床）→ chirp 区間 → chirp 終了後 1 秒（RT60 / DRR / モードピーク / 振幅）。サンプリングと特徴抽出を ストリーミングで重ねれば、生 32k サンプル全保持は不要にできる。

4. 推論アーキ移植

4.1 専門 ELM × 4 + マハラノビス

spec.html §10 で確定済の構造を実装視点で再掲:

  • ELM-AB: 扉 AB の開閉判定（必ず動作）
  • ELM-a, ELM-BC, ELM-b·c 時分割: AB 状態に応じて条件付き起動（4 スロット制約）
  • マハラノビス 14 クラス: 全候補状態に対する尤度。トポロジ判定 → 関連 ELM 起動の階層パイプライン

4.2 メモリ占有試算

項目サイズ計算合計配置
α（隠れ層重み, 固定）K × D = K × 30 × 1B (q7)K=64 なら ~1.9 KBFlash
β（出力重み, 学習対象）4 ELM × K × M_out × 2B (q15)K=64, M_out=4 平均なら ~2 KBFlash（PC 学習後焼込み）
or RAM（オンデバイス再校正版）
μ_k14 × 30 × 4B1.68 KBFlash
Σ_k⁻¹14 × 30 × 30 / 2 × 4B（上三角）25.2 KBFlash（RAM には収まらない）
推論ワーク（特徴量 30 次元 × float, 中間バッファ）~1 KB1 KBRAM
音声 / FFT バッファFFT 512 q15 + 窓 = ~2 KB2 KBRAM

主リスク: Σ_k⁻¹ 25 KB は spec §10 の Flash 数 KB 目標を大きく超える。 緩和策候補:

  • 対角近似（Naive Bayes 化）: 14 × 30 × 4B = 1.68 KB に圧縮。精度低下の影響は要評価
  • 低ランク近似（Σ⁻¹ ≈ U Λ Uᵀ, rank r=5）: 14 × (30 × 5 + 5) × 4B = ~8.5 KB
  • クラス間で Σ⁻¹ を共有（Pooled covariance）: 1 × 30 × 30 / 2 × 4B = 1.8 KB

4.3 推論レイテンシ試算

  • マハラノビス 14 クラス × D=30: 1 距離あたり D² = 900 mul + add（対角近似なら D = 30 のみ）
  • フル: 14 × 900 = 12,600 mul/add。M0+ で固定小数 1 mul ≈ 1 cycle、1 mul/add 合計 2〜4 cycle 想定 → 25k〜50k cycle → 0.5〜1 ms @ 48 MHz、目標の 1 ms ぎりぎり
  • 対角近似: 14 × 30 = 420 mul/add → 0.02 ms。安全側
  • ELM 1 推論: K × D + K × M_out。K=64, D=30, M_out=4 で 1,920 + 256 ≈ 2.2k op → 0.1 ms 程度
  • 4 スロット時分割切替: spec §10 の「数 ms 想定」は実測必須。AxlCORE-ODL の context switch ペナルティ次第

5. β の閉形式学習（AxlCORE-ODL）

v2 のキラーデモは「30 秒録音 → β 再計算 → 動作復帰」（spec.html §10 / §12 Phase 2）。AxlCORE-ODL がオンデバイスでこの最小二乗を担当する。

5.1 確認が必要な仕様（要 開発キット）

  • H 行列の最大サイズ（サンプル数 N × 隠れ次元 K）
  • λ（リッジ項）の指定方法
  • クラス重み付き擬似逆行列が叩けるか（spec §10 「不可視ラベルのクラス不均衡」対策）
  • β を Flash に焼く API、erase/program 粒度、寿命（一般 MCU は 10k〜100k 回程度。再校正頻度から逆算）
  • 停電耐性（書込み途中で落ちた時の rollback）

5.2 30 秒録音から有効サンプルを抜く処理

30 s × 16 kHz = 480k 生サンプル。これをそのまま H に積むのは N が大きすぎ。実際の流れ:

  1. 30 秒の間に chirp を N 回打つ（例: 1 秒に 1 回 = 30 サンプル）
  2. 各 chirp 応答から D=30 の特徴量を抽出（v1 と同じパイプライン）
  3. 14 クラスのうち 「現在の物理状態」のラベルを与える（センサ移動デモなら "全閉" 状態のみで OK）
  4. H ∈ ℝ^(N×K) を構築し β = (HᵀH + λI)⁻¹ HᵀY を解く

単一クラス（全閉）だけでも μ_k と β の再校正が成立するのが Solist-AI 流儀のミソ。これは v1 の自由 NN ではできない芸当。

6. 周辺ハード移植

v1 のペリフェラルv2 での扱い移植難度
PCA9685 + SG90 ×5（I²C）v2 では実機サーボ駆動は原則不要（収集データを v1 で完了済み前提）。実演デモで使う場合のみ I²C を引く低（v1 ドライバを HAL 層越しに移植）
INMP441 / MSM261S4030H0（I²S）ML63Q2557 の I/F 次第。最悪 PDM マイク（MP34DT05 等）への置換高（PDM デシメーション CPU 実装が必要）
MAX98357A（I²S TX）chirp 再生用。I²S 無ければ PWM + LPF、または別 D/A IC中
ILI9341 TFT（SPI + 4 GPIO）v2 でも結果表示に使いたい。SPI と DC/RST/CS GPIO があれば流用低
SW3 オンボードボタン（GPIO IRQ）ROHM ボードの user button + GPIO IRQ API に差し替え低
OpenSDA UART（115200 / 921600）ROHM ボードのデバッグ UART に差し替え低

7. ソフト構造の事前リファクタ（v1 段階でやる価値）

v1 のドライバ層がすでに MCXN947 SDK 依存に染まっている（fsl_* シンボル直叩き）。v2 移植時の差分を減らすために v1 段階で HAL 層を切り出しておくのが効く。

  • servo_driver: I²C transfer を hal_i2c_write(bus, addr, buf, n) に抽象化済 → v2 でも流用可能の構造
  • sai_speaker / sai_mic: fsl_sai 直叩き → v2 でも音声を扱うなら hal_audio_* 化を v1 中に検討
  • SW3 / GPIO IRQ: BOARD_SW3_* マクロ越しに参照しているので比較的薄い。v2 側 board.h で同じマクロを定義すれば main 側ロジックはそのまま流用可
  • chirp/特徴量計算: これは新規実装。v1 では NPU 上の Conv1D が暗黙に担当していた処理を、v2 では明示的に C で書く必要

8. 検証パイプライン

spec.html §12 Phase 2 の「v1 と v2 の精度比較」を成立させるための実装課題:

  • 共通評価セット: v1 で収集した 1,000 サンプル（spec §12 Phase 1）を 生 RIR としても、D=30 特徴量としても保存しておく必要
  • v2 の評価フロー: PC から D=30 特徴量を UART 経由で ML63Q2557 に流し、推論結果を受け取って混同行列を作る test harness
  • メトリック揃え: any_open 二値、door/window 多クラス、角度回帰の MSE — v1 と v2 で 同一メトリック関数を PC 側で実装（pc/eval.py 的なもの、未着手）
  • 「v1 から 5% 以内」の合否基準: クラスごと精度 / マクロ平均 F1 / 角度 MAE のどれを採用するか事前に決めておく

9. 未確認事項リスト（開発キット入手後の最優先）

  1. ML63Q2557 ペリフェラル一覧（特に I²S/PDM/I²C/SPI/UART の有無と本数）
  2. AxlCORE-ODL の入出力次元上限と β 計算 API
  3. ROHM 公式 SDK のコンパイラ・ビルドシステム（gcc 互換か、独自 IDE 必須か）
  4. Flash 自己書込み API、最小消去単位、書換え寿命
  5. クロック・パワー管理（48 MHz 連続動作で消費電流、低消費モード遷移時間）
  6. デバッグ I/F（SWD？ J-Link 互換？）
  7. 開発キット入手手段・価格・納期

10. 段階的移植計画

  1. キット入手 + Hello World: シリアル疎通、LED 点滅
  2. PC 側で特徴抽出を確定: v1 で集めた生 RIR を D=30 特徴量に変換するスクリプト（pc/training/features.py の拡張）
  3. ホスト PC で β 閉形式学習: numpy の lstsq で参照実装、AxlCORE-ODL なしでも数値的に再現できる状態にする
  4. ML63Q2557 上で推論パイプラインのみ: 音声 I/F は使わず、PC から D=30 特徴量を UART で流す → ELM ×4 + マハラノビスで分類 → UART で結果返す
  5. 音声 I/F 接続: I²S/PDM/codec を物理結線、生サンプル → D=30 特徴量の片道パイプライン
  6. AxlCORE-ODL でオンデバイス β: 同じテストデータで PC 参照実装と一致確認
  7. オンデバイス再校正デモ統合: SW でセンサ位置変更モード突入 → 30 秒録音 → β 再計算 → 動作復帰 → TFT で結果表示
  8. 精度評価: v1 vs v2 の 5% 以内検証、未達ならアーキ調整（ELM 隠れ次元 K、共分散近似精度）

11. リスクサマリ

リスク影響度緩和策
ML63Q2557 に I²S / PDM 入力が無い高外付け codec（I²C 制御 + I²S 出力）または別マイク選定。BOM 影響大
FFT / フィルタバンク計算が実時間に間に合わない中〜高FFT サイズ縮小（1024→512）、フレーム間引き、特徴量の一部簡略化
Σ_k⁻¹ が Flash に収まらない中対角近似 / 共有共分散 / 低ランク近似。精度トレードオフ要評価
ROHM SDK が独自 IDE で gcc 互換性が薄い中v1 段階で HAL 層を切り出し、移植境界を局所化
β オンデバイス計算のサンプル数不足低〜中クラス重み付き、β 初期値を PC 学習結果で warm start、L2 正則化強化
4 スロット時分割のコンテキスト切替コスト低実測後にスロット利用パターンを最適化、最悪 ELM-b・c を共通化
v1 と v2 の精度差が 5% を超える中アーキ調整（K, 共分散近似精度, λ, アンサンブル数）、達成不能なら差分そのものを成果として報告
