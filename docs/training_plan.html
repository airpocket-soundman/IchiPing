2026-05-25 更新 — 本計画は歴史記録、現状は v12345 で完了済

本ページに記載されている Phase A-F の学習ループは v12345 で実行・完了済み。MCU 実機で 14cls 100% / 32cls 100% を達成（v12345 検証レポート）。 本計画当初の前提だった「14-class softmax 単ヘッドが情報理論的に最適、32cls は ~0.44 で頭打ち」 の予想は経験的に否定され、現在は 14cls / 32cls 両 head 共存運用（用途別使い分け）が採用されている。

本ページはワークフロー設計の参照として残しているが、最新の実績は v12345 検証レポート / head 設計比較 / v1 学習結果 を参照のこと。

入力データ形式の選択 — 本計画は 1D FFT を baseline とする

features.py は WAV を整合フィルタで畳み込んだ後に FFT を取り、 1024 bin の 1D log-magnitude スペクトルに変換する。 モデルは Conv1D ベースの ~13.7 K params NN （NN 設計 通りの構成）。

観点1D log-mag (現状)2D STFT (将来オプション)
ホワイトノイズ励振との相性 ◎ 定常確率で時間軸に情報なし → 1D で十分 △ 時間軸が冗長
chirp 励振との相性 ○ 整合フィルタ後の RIR を 1D 化すれば等価 ◎ 時間-周波数構造を直接保持
MCXN947 NPU 負荷 ◎ Conv1D は軽い △ Conv2D は 1 桁重い
実装枯れ度 nn_design.html で v1 baseline 確定 nn_review §3.2 で「注目候補」段階

走査音方式 (D-1) で ホワイトノイズが選ばれれば 1D が最適。chirp が選ばれた場合は 1D（整合フィルタ後）+ 2D STFT 並走比較を検討する余地がある。

2D への切替コストは小さい: 変更するのは features.py（出力 shape）と model.py（Conv1D→Conv2D）の 2 ファイルのみ。 dataset / augment / train / infer / export_onnx / quantize は tensor shape 非依存で再利用可能。 走査音確定後 1 時間で並走比較セットを作れる疎結合設計。

1. サンプル所要量

フェーズ 状態あたり 総数
(32 真状態)		 拡張後 effective 計測時間 用途
PoC 10 320 ~2,000 ~8 分 動作確認、loss が下がるかの sanity
本収集 v1（推奨） 30 960 ~5,000 ~25 分 学習可能な実用モデル
本収集 v2 100 3,200 ~20,000 ~80 分 高精度・頑健化

根拠

  • 14 等価クラス × 30 = 420: 経験則「params ≤ data × 10」に対し、30 K params の NN なら data = 数千 effective で十分汎化
  • 32 真状態 × 30 = 960: 観測等価クラス内の機械バラツキ（サーボ位置 ±2°、扉パネル微差等）が 自然な augmentation として機能する → クラスあたり実効 30 × 8 = 240 サンプル相当
  • ×5 拡張: TimeShift（±10 ms）/ LevelJitter（±2 dB）/ NoiseOverlay（SNR 10-30 dB） / GaussianHiss で 1 サンプルあたり 5 通りの摂動 → 5,000 effective
  • 14 クラス macro-F1 ≥ 0.90 が目標。届かなければ本収集 v2 に進む

2. 反復ループ — Train / Eval / Deploy

A実機 収集 — 960 サンプル取得

所要 ~25 分（initial + 改善ごとに再収集も可）
uv run python collector_client.py --port COM3 \
    --plan plans/full_32_v2.yaml --run-id full_32_v2

出力: captures/full_32_v2/sXXXXX/frame_*.wav ×960

BPC 学習 (FP32) — 14-class softmax 1D-CNN

所要 5-10 分（RTX 4060 想定、CPU でも 30 分程度）
uv run --extra training python -m training.train \
    --captures captures/full_32_v2 \
    --out runs/v1 --epochs 50

出力: runs/v1/best.pt（PyTorch ckpt）/ train_log.csv（per-epoch loss）/ config.json（再現用メタ）

モデルは NN 設計 の IchiPingV1 （Conv1D 16/32/64 ch + GAP + Linear(64, 14) + softmax, ~13.7 K params）。 損失は cross-entropy 1 本。Augmentation は augment.py の default_train_transform が silence_2cond_v1 の TV ノイズを自動 overlay。

CPC 推論で検証 — 14 クラス macro-F1 + 混同行列

所要 ~1 分
uv run --extra training python -m training.infer \
    --captures captures/full_32_v2 \
    --ckpt runs/v1/best.pt \
    --out reports/v1_eval/

出力: report.json（per-bit accuracy / per-class F1 / overall）/ confusion.csv / confusion_matrix.png

判定: macro-F1 ≥ 0.90 なら D に進む。届かなければ:

  • 混同行列で「A1 と A2 を取り違える」→ 窓 a 開閉特徴が弱い → 走査音帯域 / ROI 見直し
  • 「B1-B4 内で B2 と B4 を取り違える」→ 扉 AB 開状態の窓 a 検出失敗 → 同上
  • クラス全体で F1 が低い → サンプル数増（v2 へ）or augmentation 強化

C′実機ライブ推論で動作確認（任意・推奨）

所要 ~5 分（インタラクティブ）

captures データだけでなく、実機 + サーボを動かしながら推論結果を見る 検証ステップ。Phase C のオフライン F1 が良くても、ライブで取った フレームに対する挙動を見ておくと「ハマる状態」が早く見つかる。 

# 連続モード — Ctrl-C で停止、サーボを手で動かして予測の変化を観察
uv run --extra training python live_infer.py live \
    --port COM3 --ckpt runs/v1/best.pt --pattern chirp_200_6k --interval 1.5

# plan で 32 状態を自動掃引して per-class 精度を出す
uv run --extra training python live_infer.py verify \
    --port COM3 --ckpt runs/v1/best.pt \
    --plan plans/full_32_v2.yaml --pattern chirp_200_6k

live_infer.py は MCU を Ping → 1 フレーム受信 → 学習と同じ features.py で前処理 → モデルで予測 → 14 クラスラベル + 確信度を出力。 live / single / verify の 3 サブコマンド。

DONNX エクスポート + INT8 量子化

所要 2-3 分
# D-1: PyTorch → ONNX (opset 13, fixed shape)
uv run --extra training python -m training.export_onnx \
    --ckpt runs/v1/best.pt --out runs/v1/best.onnx

# D-2: INT8 量子化 (eiq-onnx2tflite, 推奨)
uv run --extra training python -m training.quantize \
    --onnx runs/v1/best.onnx --out runs/v1/best_int8.tflite \
    --captures captures/full_32_v2 --backend eiq

判定基準: FP32 比 macro-F1 が -2 pt 以内なら採用。落差が大きい場合は:

  • --per-channel 量子化を有効化（デフォルトで ON）
  • QAT (quantization-aware training) に切替: 学習時に fake-quant 挿入
  • backbone のチャネル幅を増やして冗長性を持たせる

詳細は NN 考察 §1.A ONNX→Neutron パイプライン参照。

ENeutron Converter → MCXN947 用 TFLite

所要 ~2 分（Windows / eIQ Toolkit CLI 環境から）
eiq-converter --plugin eiq-converter-neutron \
              --custom-options "target mcxn94x" \
              runs/v1/best_int8.tflite \
              runs/v1/best_neutron.tflite

生成 TFLite は NeutronGraph という単一カスタム op に NPU 対応部分が集約される。 CPU フォールバックが必要な op（Softmax 等）は元の op として残る。

2.5. 32-class softmax は本番モデルとして採用 (歴史記録)

結論 (v12345 で確認): 32-class softmax は MCU 実機 100% accuracy を達成し、 本番モデルとして 14cls と並列に運用される（用途別使い分け、 NN 設計 参照）。 当初の「観測等価性で ~0.44 が天井」予想は経験的に否定された。原因は実扉が完全遮音ではなく -20〜-30 dB 減衰程度で、サブ状態にも分離可能なシグナルが残っていたこと （nn_methods_compare §1）。
  • モデル: model_32cls_neutron.py — Neutron 互換アーキ (Conv2D + AvgPool + 1×1 Conv head)、XL サイズ ~104K params
  • 学習: train_32cls.py （--baseline-override-dir / --baseline-jitter-dirs で baseline jittering aug を有効化）
  • 達成精度（MCU 実機 sweep, n=32）:
    • v12345_BLJIT_live: 32cls 100% / 14cls 100%
    • v12345_BLJIT_factory（校正なし）: 32cls 88% / 14cls 100%
    • v12345_50f_live_noiselow（騒音下校正）: 32cls 100% / 14cls 100%

32 クラス学習コマンド

uv run --extra training python -m training.train_32cls \
    --captures captures/full_32_v2 \
    --out runs/v1_32cls --epochs 50

# 推論
uv run --extra training python live_infer.py live \
    --port COM3 --ckpt runs/v1_32cls/best.pt --arch 32cls \
    --pattern chirp_200_6k

判定 (実績)

本表は当初予想と実測の対照（観測可能性仮説の検証記録）:

当初の 32cls 予想当時の解釈実際の結果
≤ 0.44 (≈ 14/32) 観測可能性予言通り → 等価クラス内に区別シグナルなし —
0.45 - 0.65 予言を多少超える —
≥ 0.65 予言が大きく崩れている → 観測可能性モデルが間違っている可能性 v12345_BLJIT_live で 32cls 100%。予言は経験的に否定された。 扉が完全遮音ではなく -20〜-30 dB 減衰程度 → サブ状態にも分離可能シグナル残存。

3. ゲート基準（次の Phase に進む / 戻す）

進む条件戻る条件戻り先
A → B: 全 32 状態 × 30 サンプル取得完了、CRC OK 率 ≥ 99 % CRC エラー多発、外れ値が複数状態に出る 計測環境 / 走査音 / 模型の見直し
B → C: 50 epoch で train loss が plateau に到達 loss 発散、val loss が train から乖離 learning rate 調整、batch size 増減
C → D: 14 クラス macro-F1 ≥ 0.90、扉 AB 精度 ≥ 0.95 F1 < 0.85、特定クラスが混同行列で集中誤分類 サンプル数増 (v2) / augmentation 強化 / ROI 帯域見直し
D → E: INT8 量子化後 F1 が FP32 比 -2 pt 以内 量子化で -5 pt 以上の精度低下 QAT 採用 / per-channel 量子化 / backbone 増強
E → F: Neutron Converter で NPU 化エラーなし、サポート外 op が NeutronGraph 内に残らない op がサポート外でフォールバック モデル定義から該当 op を除外（§1.2 op リスト参照）
F → 完了: MCU 上で推論レイテンシ ≤ 100 ms、メモリ使用 ≤ 96 KB レイテンシ過大、メモリ不足 backbone 簡素化 / 入力解像度低下 / 量子化スキーム見直し

5. Augmentation 戦略

augment.py の default_train_transform() が学習時に各サンプルに適用する確率的変換:

変換確率パラメータ目的
TimeShift 0.7 ±10 ms 周期的シフト chirp 開始タイミングのジッタを吸収
LevelJitter 0.7 ±2 dB ゲイン変動 SPK 音量・マイクゲインのドリフト耐性
NoiseOverlay
(ambient あり時)		 0.6 SNR 10-30 dB で実環境ノイズを重畳 展示会場等の雑踏耐性
GaussianHiss
(ambient なし時)		 0.5 SNR 15-35 dB の白色雑音 ambient が揃う前の代替

Phase A 再計測のたびに ambient WAV も追加することで NoiseOverlay の多様性が増し、頑健性が向上する。 当面の実行計画 Step A で取得した silence_quiet / silence_tv が初期 ambient 源として直接使える。

6. v1.5 雑踏適応との接続

本ループで v1.0 モデルが固まったら、配置先（展示会場等）で雑音 30-60 秒録音 → PC で head fine-tune → MCU flash 書き換え、の運用フローに移る。 詳細は NN 考察 §7 v1.5。

本計画と v1.5 の関係:

  • 本計画 (v0.6 - v1.0): 開発環境で 14 状態を 90 % 以上で当てる学習を完成
  • v1.5: 展示会場到着後 10 分で「その会場の雑音」に適応した派生モデルを生成
  • 共通: training/quantize.py + Neutron Converter のパイプラインは同じ
  • 差分: v1.5 では backbone を freeze し FC ヘッドだけ少サンプル (~30 件) で fine-tune するモードを追加
