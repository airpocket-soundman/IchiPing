2. 特徴量 — Welch スペクトル

PRBS 励振では時間-周波数構造が無いので、chirp 経路（matched filter で RIR 抽出）は使えない。 代わりに 2 s の波形を Welch 法で平均パワースペクトル化して 1024 bin log-magnitude 特徴量に変換する。実装は pc/training/features.py の samples_to_noise_features()。

パラメータ値備考
窓関数Hannサイドローブ抑制
セグメント長2048 sample128 ms @ 16 kHz
オーバーラップ1024 sample50%
セグメント数302 s 中で平均
出力ビン数1024rFFT 1025 ビンから DC を除外
正規化10·log10 + mean-subtractchirp 経路と同じシグネチャ
フロア-80 dBlog の発散防止

入出力形状（1024 次元 float32, 平均 0）は chirp 経路と完全一致。 したがって 1D-CNN backbone は 2 つの励振方式で共有でき、 device 側 (MCXN947) でも PowerQuad-FFT を Welch に流用すれば同じパイプラインで動かせる見込み。

5. 学習カーブ

60 epoch 分の train / val 推移。上段 = cross-entropy loss、下段 = 32-class accuracy。 val accuracy は epoch 29 付近で 1.000 に到達し以降ほぼ張りつき。loss は最後まで滑らかに下降している（train_loss 3.41 → 0.18 / val_loss 3.40 → 0.06）。

途中で val_acc が一瞬 0.9 付近に落ちている epoch（28, 31, 40, 43, 53 など）は Dropout + augmentation の確率性の揺らぎで、loss 側は単調減少しているので過学習や発散ではない。 最終 val_loss 0.057 は 32-class なので perfect-confidence に近い。

8. 限界と次にやるべきこと

⚠️ Test 精度の解釈

70/15/15 のランダム分割は同一 run_id の 30 連続フレームを混ぜているので、test サンプルは train サンプルと時間相関が強い。真の汎化評価には別 run でのデータが必要。 1.000 という数字を device 性能の保証として持ち出さないこと。

次にやるべきこと

  1. 別 run でのクロスバリデーション — 同じ 32 状態 × 30 フレームをもう 1 回別日に撮って full_32_train_v2 として保存、train_v1 で学習 → train_v2 で評価。 これで真の generalization を測る。
  2. D-1〜F フェーズ（MCU デプロイ）への移行 — ONNX エクスポート → INT8 量子化 → Neutron 変換 → firmware/10_inference 統合。所要 2–3 日。
  3. 14-class softmax 専用モデル — 現状 32-class で訓練後に畳み込んでいるが、 初めから 14-class で学習する方が出力エントロピーが理論限界 (log₂14) と直接対応する。 NN 設計ドキュメントの推奨実装。

9-3. 所見

✅ 8 割は generalize する

train と test を別日で取り直しても 14-class acc 0.812 をキープした。 test split で出た 1.000 は時間相関に底上げされた数字だが、 モデル自体は noise 励振による 系の伝達関数を 実体としてある程度学習できている。 特に A2 と C 系の半分は別日でも完璧。

⚠️ B クラスが脆い

B1 / B2 / B4 が全 miss。B 系は「扉 AB 開・扉 BC 閉」共通でリビング A + B 部屋までは 音が届く条件。train_v1 段階でも intra-class σ の中で B 系は member 数 2 しかなく学習信号が薄かった。 cross-run でその脆さが顕在化した形。

誤分類の方向を見ると B → A1 / C 系に偏っており、 「扉 AB の開閉判定だけは day-to-day で不安定」が現状の主な失敗モード。

🚫 受動 listening では学習効果ゼロ

passive_v1（SPK off, TV 雑音床のみ）に対しては 14-class acc 0.031 = 完全ランダム。 予測がほぼ C8 に偏ったのは入力の log-magnitude 平均が大幅に違うため最終層 bias が引いてるだけ。 モデルは励振信号の存在に強く依存していることが裏返しで確認できた。 本番運用でも能動励振を前提に置くべき（passive 経路は v1.5 以降の課題）。

9-4. 結論と必要な対策

  • 「真の汎化性能 ≒ 81%」を v1 の公式数字として扱う。 §8 の test 1.000 は今後 train/test 同一 run である限りこの程度の楽観値が出ると認識しておく。
  • B 系の改善には 同条件でもう 1〜2 run 撮って学習側の B 系メンバ数を増やすのが最も直接的。 train_v1 段階で B 系は class あたり 2 状態 × 30 frame = 60 サンプルしかない。 もう 1 run 足すと 120 → 学習信号が倍になる。
  • クロス-run の頑健性が日 (温度・湿度・家具配置) と相関しているなら、 SPK 励振の calibration（spk_eq の再測定）を本収集前に毎回かける運用も検討。 現状 EQ disabled で運用しているが、SPK 周波数特性のドリフトが B 系の脆さの原因かもしれない。

10. 14-class softmax 単ヘッド版（NN 設計の本命）

§1–9 までは 32-class softmax で学習し評価時に等価クラスへ畳み込んでいた。 これは model_32cls.py の 「等価クラス内サブ状態をモデルが拾えるか」を確認する実験用設計。 NN 設計の本命は 初めから 14-class softmax 単ヘッドで学習する形で、 情報理論的上限 (log₂14 ≒ 3.81 bit) と直接対応する。今回新たに model_14cls.py + train_14cls.py を実装して同じ条件で学習・評価したので、両者を並べて報告する。

10-5. なぜ 14cls の方が cross-run でわずかに劣ったのか

仮説: 32cls の "不可能タスク学習" が偶発的に汎化を助けた

32cls は等価クラス内で原理的に判別不能な 8 メンバ (A1 など) を頑張って区別しようとする 悪条件タスクを背負っていた。これがある種の 正則化 / 暗黙のデータ拡張として働き、 cross-day で B 系スペクトルがズレたときに偶然「近い A1 サブ状態」と判定して 結果的に A1 (= B からの誤り先) に振れ、F1 を 0 に落ちきらない救済が起きた可能性がある。

14cls は最初からクラス境界だけ学ぶので、cross-day で境界の外に出たサンプルは 迷わず誤分類される。これは数字としては悪く見えるが、原理的な振る舞いとしては 14cls の方が正しい: 識別不能な対象を識別しようとする 32cls の方が むしろ「期待しない情報源 (微小ドリフト)」に依存していることになる。

B クラス問題は head の選択では解決しない

両モデル共通の失敗パターン (B1/B2/B4 全 miss) は、train データ側の B クラス member 数不足が根本原因。class あたり 2 状態 × 30 frame = 60 サンプルしかなく、 cross-day でクラス境界が動いた瞬間に対応する学習信号がない。

解決には:

  • 同条件で run_id を増やして B 系のメンバ多様性を上げる (train_v2, train_v3 ...)
  • spk_eq 再キャリブレーション運用で日々の SPK ドリフトを補正
  • augment 強化: SpecAugment 系の周波数マスクで spectral drift に耐性

これらは head 設計とは独立に効くので、v1 本命としては 14cls を採用しつつ データと augment 側で B 系を強化するのが正しい方向。

10-6. 結論

  • v1 本命は IchiPingV1_14cls (model_14cls.py) — 学習収束 3 倍速 + 出力意味論が NN 設計と一致。
  • cross-run noise の 0.750 は 32cls の 0.812 より下だが、本質的な振る舞い (B 系 miss) は両者同じ。差分は 32cls の偶発正則化分にすぎず、構造的優位ではない。
  • MCU デプロイ (ONNX → INT8 → Neutron) の対象は 14cls 版を採用。13,790 params で 32cls (14,960) より更にコンパクト。
  • cross-run 性能の本格的な改善は B 系データ拡充 + spk_eq 再校正で別途取り組む。

11. 特徴量を「baseline からの diff」に変えてみる

§10 までで「B 系の cross-day 脆さはデータ不足が根本」と書いた。 だが本当にそうか確かめるため、特徴量側を 1 段強化してみた: 各 frame の log-magnitude PSD から、そのデータセット自身の s00000 (全閉) 平均を per-bin 引く。 全体音量シフトが消え、純粋に「全閉に対する周波数応答の差分」だけが残る形になる。 実装は features.py の samples_to_noise_diff_features() + dataset 側で run ごとの s00000 平均を 自動計算（dataset.py）。

この前処理は chirp 解析 や noise 解析 の overview ヒートマップ (FFT diff from baseline) と原理的に同じ。可視化で特徴を強調できているなら モデルにとっても判別しやすいはず、という仮説。

11-4. 何が起きたか

✅ B 系の救済は SPK ドリフトの除去で大半が解決

14cls noise → noise_diff で B 系の正解数が 0/8 → 7/8 に跳ね上がった (n=2 × 4 クラスのうち B4 の 2 つだけが残った形)。 §10-5 で「32cls の偶発正則化が B3 を救った」と書いたが、 今回の結果から見れば 真の犯人は per-run の絶対 dB レベルドリフトだった。 各 run の s00000 をベースラインに引き算することで、SPK の温度ドリフト・ マイク位置誤差・収集時間帯の電源ノイズ等が消え、door 開閉による per-bin の 形状変化だけがクリアに残る。

⚠️ B4 だけ残った理由

B4 = (a, b, c, AB, BC) = (1, 1, *, 1, 0) ＝ 窓 a/b 同時に開 + 扉 AB 開 + 扉 BC 閉。 Room A の窓 a と Room B の窓 b が同時に開く唯一の B クラスで、 train_v1 内のスペクトル σ_state を見ると B クラス内で最も大きい (B4 σ_state = 0.383 dB vs B1 0.453 / B3 0.352)。 つまり「真の B4 状態自体が train 内でも揺らいでいた」ので、 cross-day で更にズレると判別境界の外に出やすい。 対策はやはり train データの B4 サンプル増量か、 augmentation で B4 周辺を厚く撒くこと。

🎯 デプロイ運用への含意

noise_diff 経路は 「各家・各日に最初の 1 回 s00000 録音を取って baseline にする」 というキャリブレーション工程を前提とする。これは IchiPing の運用シナリオ （設置時に家ごとにキャリブレーションする想定）と相性が良い:

  • 設置直後: 全閉状態を MCU 側で要請 → s00000 録音 → ベースライン log-mag を flash に保存
  • 運用時: 録音ごとに log-mag を取り、保存したベースラインを per-bin で引く
  • 季節変化や家具配置変更があれば、ユーザ操作で baseline 再取得

必要な flash サイズは 1024 × 2 byte (INT16) = 2 KB、または float16 で 2 KB、 INT8 量子化なら 1 KB。MCXN947 の SRAM/Flash に問題なく載る。

12. 特徴量空間 augmentation で B4 を解く

§11 の noise_diff で B 系の 3/4 (B1, B2, B3) は解けたが B4 だけ残った。 サンプル数不足説と表現力不足説の両方が候補に挙がった中、まず augmentation 強化で「同じデータを擬似多様化」する方を先に試した。

12-1. 既存の波形 augmentation はノイズ励振でほぼ無効だった

augment.py の default_train_transform は元々 chirp 励振想定で書かれていて、PRBS ノイズに対しては:

  • TimeShift: PRBS は shift-invariant なので Welch スペクトル不変 → no-op
  • LevelJitter: BatchNorm で大半吸収される → 効果薄
  • GaussianHiss: SNR 15-35 dB は +0.0003〜0.13 dB 程度の dB 棚上げ → 弱い

12-2. 追加した特徴量空間 augmentation

Welch スペクトル化した 1024-bin の特徴量に対して直接効かせる SpecAugment 系 2 種類を追加した (augment.py 末尾 FreqMask / SpectralJitter / default_feature_transform):

変換パラメータ確率狙い
FreqMask連続 1–60 bin × 2 回マスク (0 で埋める)0.7単一 bin への過剰依存防止 / 帯域欠落耐性
SpectralJitterper-bin Gaussian σ=0.3 dB0.8SPK 周波数応答の日々のドリフト擬似化

σ=0.3 dB は実測の cross-day intra-class σ_state (0.4–0.6 dB) と同オーダーに揃えた。 これより大きいと真のクラス境界も埋もれる、これより小さいと cross-day での spectral drift をシミュレートしきれない、というバランス。

12-5. 何が起きたか — サンプル数不足ではなく "表現多様性" の不足だった

✅ ユーザー提案の検証結果

B4 残存の原因として (a) サンプル数不足、(b) モデル表現力不足 (50 Hz 幅の peak 検出には GAP 解像度 250 Hz が荒すぎる)、(c) augmentation 無効 の 3 つが候補に挙がっていた。今回の実験で (c) が真因と判明。 モデルアーキテクチャはそのまま、訓練時の特徴量変動を増やすだけで完全分離達成。

解釈: 13,790 params のモデルでも 1150–1200 Hz の微小 peak を識別する capacity は既にあった。ただし train_v1 だけだとその peak は「固定位置」 で出現するため、cross-day で peak 位置が ±50 Hz 程度ずれると認識できなかった。 FreqMask が「peak が消えても他の bin で代替する」訓練を、SpectralJitter が 「peak の絶対 dB が ±0.3 dB ぶれても拾う」訓練を与えた結果、 cross-day の小ドリフトに頑健になった。

⚠️ 解けたとは言え caveat あり

noise_v1 の cross-day サンプル数は 1 状態あたり 1 frame なので、 B 系 = 2 サンプル、C 系 = 1 サンプルしかない。「32/32 ぴったり通った」も 統計的に薄い。本来は cross-day を REPEATS=30 で再収集して 32 × 30 = 960 frames で評価すべき。 現状の 1.000 は「方向性は確認できたがマージンは未測定」という認識でいる。

📌 アーキテクチャ拡張 (GAP 廃止 / 層増加) は持ち越し

ユーザー観察「1150–1200 Hz の差を識別するには GAP の解像度 250 Hz では 粗すぎる」は正しい指摘だったが、結果として aug で代替できた。 GAP 廃止 + Flatten 化は params が +25k になり MCU 制約が厳しくなる方向なので、 cross-day 1.000 が崩れない限り見送り。今後 train_v2/v3 と組み合わせて 更に難しい cross-house 評価で割れたら、その時点でアーキテクチャ拡張に進む。

truepred違い意味
s11010 (B4)s11111 (C8)c=0→1, BC=0→1窓 c も扉 BC も「閉→開」

共通失敗モード: 「扉 BC 閉 → 開」と誤判定

3 件すべて 扉 BC の閉↔開境界で外している。これは観測等価クラスの定義そのもの: BC が開けば Room C 由来の周波数応答が加わり 14-class B → C へ移行する境界。 32cls 学習だと 5 bit すべてを当てに行く広い学習信号に分散するため、 BC bit に集中した識別シグナル (B/C 境界の細かい peak 違い) が他の bit (b, c) と トレードオフされて弱まる。14cls 直接学習だと BC 境界の差分が直接 loss に効く ので、この境界が硬く保たれる。

13-4. v1 head 選択の確定根拠

  • 14cls 直接: cross-day 1.000 (32/32)、macro-F1 1.000、params 13,790、収束 epoch ~10
  • 32cls 同条件: cross-day 14cls 0.906 (29/32)、macro-F1 0.845、params 14,960、3 件すべて B → C 境界で miss
  • 差の本質: head の出力構造が直接 cross-day robustness に効く。32cls の "サブ状態予測" は 情報理論的に不可能な目標を含むので、可能な目標 (等価クラス境界) の学習信号を希釈する
  • v1 デプロイ対象は IchiPingV1_14cls で決定。MCU 容量・推論速度・cross-day 性能すべて 14cls 優位
